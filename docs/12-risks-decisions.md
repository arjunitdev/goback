## Decisions resolved for the M0–M1 pilot (2026-10-30)

| ADR | Decision | Rationale |
|---|---|---|
| ADR-003 | Site access is an **optional** host permission requested on activation. Content scripts are registered dynamically (`chrome.scripting.registerContentScripts`) only while a site is enabled, permitted and not killed. | Least privilege; lets the stylesheet paint at `document_start` without an async storage lookup. Verified in the Playwright suite. |
| ADR-004 | Responsive/mobile web is deferred. | Out of scope for first release (docs/01 §1.5). |
| ADR-005 | Diagnostics are local-only, allow-listed event counters (names, never page content). No export in the pilot. | docs/08 §8.2. |
| ADR-006 | Pilot supports `https://www.google.com` only. Regional domains are native until separately researched. | Avoids unverified locale layouts and broad host patterns. |
| ADR-008 | Minimum Chrome version 120. | Dynamic content-script registration, `:not()` complex selectors and the new headless test mode are all available. |
| ADR-011 | Two build flavors. `dev`/`test` include a recreated look-alike wordmark (independent artwork, CSS-only swap). `store` excludes it and `scripts/audit-package.mjs` fails the build if it appears. | The user wants logos; trademark/copyright exposure of look-alike marks is unresolved (ADR-010), so they must not reach a public package without legal review. |
| ADR-012 | The 2012 colour palette applies only when the engine measures a **light** page (`data-retroweb-scheme='light'`, from the page's own background). Dark pages get shape/typography only. | Found live: a forced white body made Google's light-on-dark header unreadable. A test requires every colour rule to be scheme-gated. |
| ADR-013 | Adapters may set `earlyStyle: false` and declare `forbidden` probes. Facebook does both. | The first paint at `/` may be a login wall, which FR-012 forbids restyling. |
| ADR-014 | Probe retry window is ~20s (0.4, 1.2, 3, 6, 10s) before failing open. The Playwright build uses 3×150ms. | Found live: YouTube rendered a route after ~5s on a cold load, and the earlier ~4.6s window wrongly dropped the theme. |
| ADR-015 | Site access is a per-site optional host permission for `www.google.com`, `www.youtube.com`, `www.facebook.com` only (no regional or sub-domains). | Least privilege (R08). Regional domains need separate research (ADR-006). |

| ADR-016 | Archive-derived assets (the real 2012 YouTube logo and paper texture) are allowed **only** as private, git-ignored files in `src/assets/private/`, used by non-store builds on the owner's machine. They are never committed, pushed or packaged for the store; the build, registration logic and store audit each enforce this independently, and tests pin it. | The owner asked for the exact logo. Distributing it would infringe trademark/copyright (ADR-010), so personal use is the only safe form. |

| ADR-017 | Authentic mode renders YouTube in its LIGHT theme even for dark-theme accounts, by pinning YouTube's ~380 colour variables to their light values (`scripts/gen-youtube-theme.mjs`, regenerated on demand) and holding the `dark` attribute off <html> and the masthead. Compatibility mode keeps the user's theme. If the pin goes stale the engine measures the page as dark and withholds the 2012 palette, so text stays readable. | The 2012 site had no dark theme and the owner's account is dark. Found live: removing the `dark` attribute alone does nothing, because YouTube serves the dark values straight on <html>. |

| ADR-018 | YouTube Authentic mode fills the window instead of reproducing the 970px column: the masthead spans the screen, the 200px dark guide is fixed to the left edge for the full window height, and the home/results content and the watch player use the remaining width. The home feed keeps YouTube's own grid. Colours, fonts, button shapes, logo and the dark guide stay 2012. | The owner found the 970px column wasted most of a modern screen and preferred the full-width grid layout. Layout fidelity to the 2012 column is traded for usability; typography and palette fidelity are unchanged. |

| ADR-019 | The engine keeps the theme painted across same-site route changes for CSS-only adapters (`keepOnRouteChange`, YouTube) and runs DOM-mutation work (scheme measurement, probes) at most once per second while healthy; unhealthy pages are still checked every batch. The first mount no longer clears and re-sets the attributes the early script already applied. | Measured live on YouTube (search, then click a video): the extension added ~110ms style and ~100ms layout per navigation and ~700ms of long tasks, because every click rebuilt the theme and every DOM batch forced a style flush. After the change the navigation cost matches a no-extension baseline. The page-wide font rule was measured and is NOT a cost. |

| ADR-020 | The YouTube watch column is one grid sized by YouTube's own player-width formula (`--ytd-watch-flexy-max-player-width`), so title, owner row, buttons, view count and description share the player's left and right edge. The view count sits top-right of the action row with a green/red bar under it. The bar is a **decorative placeholder** drawn with `::after` (about 90/10), not data: YouTube no longer exposes dislike counts. | The owner asked for the 2012 alignment and a placeholder bar. The player itself is never styled (exclusion guard); alignment comes from sizing its siblings. A bar showing a made-up ratio could mislead, so it is documented as non-data here and in the evidence ledger. |

| ADR-021 | YouTube click latency: the engine watches only the direct children of `ytd-page-manager` (`observeShallow`), not the whole page subtree, and the navigation progress bar is 4px instead of 2px. Preloading/prerendering the next video was evaluated and rejected. | A click on YouTube costs about 1s, of which the extension was a small share (A/B on the live site, results->watch and watch->watch). A subtree observer pays a record per node YouTube inserts. Prerender needs a full document load (~4s measured) while YouTube's own in-page navigation takes ~1s, and prefetching videos the user has not opened would add network requests and tracking-visible traffic that PRIVACY.md and the "no unexpected requests" test rule out. |

| ADR-022 | Watch-column sizing is `min(100%, max(640px, (100vh - 250px) * width-ratio / height-ratio))` (YouTube stores 16:9 as 16 and 9, 4:3 as 1 and 0.758, so both variables are required; dividing by height-ratio alone gave a 640px column on every widescreen video): never below the player's own 640px minimum. The grid's right track is `clamp(150px, 30%, 230px)`, and every flattened child of `#below` spans the full width. If a watch page jumps down by itself and the person has not scrolled or pressed a key, the adapter scrolls it back to the top (4 checks in 5s). | Found from the owner's screenshot: at 150% display scaling the window is ~1020x586 CSS px, the formula gave 440px, the 640px player spilled out of its column and the title, owner row and comments were crushed to ~210px. Reordering puts the player lower, so YouTube focusing it scrolled the page down (0 vs 184px, intermittent, only with the extension). Earlier checks used only 1750-1920px-wide windows. Now reproduce at 1530x879 and 1020x586@1.5. |

| ADR-023 | Google home follows the owner's March-2013 reference: the page is held light in Authentic mode by 62 generated CSS-variable pins (`gen:google-theme`); the real 2013 logo is a private, archive-derived asset (non-store builds only, same three guards as YouTube); and the extension adds two small marked link groups on the home route only (the black services bar and "Advanced search / Language tools"), built with `createElement`/`textContent`, fixed https Google addresses, removed on route change, mode change and unmount. | The owner asked for the exact 2013 page. Google no longer has these two elements, so CSS alone cannot restore them. They add no permissions, requests or scripts. The existing page is not hidden, moved or replaced. This is the first DOM the extension adds, so it is tested separately (`google-chrome.test.ts`). Results pages are unverified. |

| ADR-024 | Google results and Images pages (Authentic mode, light) get the 2013 look: the same black services bar (added once, marked, removed on route change), Arial throughout (icon fonts and SVG excluded), a square 1px search box, square panels and buttons, blue titles, green URLs, a 2013-style logo in the header, and the footer in grey. AI Mode (`udm=50`) stays native; `udm=2` is the Images route. A read-only legibility check (`legibility.ts`) fails the page open to native if a quarter of the visible text has contrast below 2:1, as a safety net for panels Google hard-codes. | The owner supplied a solved CAPTCHA, so the results page was seen live for the first time (2026-11-01, desktop 1280x900, signed out). AI Mode and Overview panels hard-code dark-theme text and could not be pinned light, so AI Mode is left alone and the guard covers the rest. The left rail, AI Overview and "People also search for" boxes still exist (restyled, not hidden). Layout varies by A/B bucket; only one bucket was checked. |

| ADR-025 | YouTube follows the owner's 2014 reference (the "Shake It Off" watch page and guide) instead of the March-2012 layout for everything it conflicts with: grey page `#f1f1f1`, white masthead, Roboto, the player first with one white card (title, channel, red Subscribe, views and like bar, actions) and a separate description card, a 402px white "up next" column (shrinks with the window so there is never a sideways scroll), and a white guide with red icon tiles and a red uppercase section heading. The 2012 reorder (title above the player) is superseded. The paper texture is dropped. | The owner supplied archive screenshots of the 2014 layout and asked for the site to be updated to match. Two real bugs found while testing: the "description interaction" layer is a full-page overlay, and painting it white hid the whole page (the card is `ytd-text-inline-expander`); a fixed sidebar width forced a sideways scroll at 1020px (now `clamp(260px, 100vw - 760px, 402px)`). Tested signed out at 1020x586, 1280x720, 1530x879 and 1907x940, on watch, home, results, channel and playlist. Not covered: signed-in pages, ads layouts that Google varies, and the "Browse/Upload" links that no longer exist. |
| ADR-026 | Facebook gets the blue header bar in two places, as the owner asked (reference: the 2015 login page and their own signed-in screenshot). (1) **Logged-out landing page**: one empty, `aria-hidden`, 48px-high bar (`#rw-fbbar`) is added as the last child of `<body>` when Facebook's own `form#login_form` is present and no checkpoint form is; it sets `data-retroweb-bare` on `<html>`, which switches off every rule that restyles the page, including the shared focus ring and reduced-motion rules in `base.css`. The login form, its fields and its buttons are never moved, restyled or read. This is a **narrow exception to FR-012**; every other authentication, checkpoint and security page, and any bare password field, stays fully native. (2) **Signed-in pages**: the `[role=banner]` header is blue with white text and icons on light **and dark** themes (those rules set their own background and text together, so they are exempt from the light-only colour test). | The owner chose "bar only" over moving the login fields into the bar, which would have meant restyling the real login form with fragile CSS. Verified on the live logged-out page (blue bar, form untouched, no extra focus ring) and on synthetic fixtures for the landing page and a dark signed-in shell. **Not verified**: the real signed-in header. No test account was available, so its logo selector (`a[aria-label='Facebook']`), whether Facebook paints the header colour on the banner itself or on an inner element, and the dark-theme result are unconfirmed. |
